PART 0 — START-THE-CLOCK ITEMS (do TODAY, in parallel)
================================================================================
These have external waiting periods. Nothing else you do matters for the PUBLIC

0.1 [YOU][WAIT ~1–3 days] Buy/confirm the domain you'll use for the API and site.
    You already control trydoppl.com. You will use a subdomain, e.g.

0.2 [YOU][WAIT ~1–2 weeks] Apple: you said you enrolled in the Apple Developer

    Google Cloud project, configure the OAuth consent screen, and SUBMIT it for

0.4 [YOU][WAIT: days + weeks of "warm-up"] Email provider: sign up for a

0.5 [YOU][WAIT ~1–5 days] Legal entity (for PUBLIC launch / taking money): form a

0.6 [YOU][WAIT ~days] Business email inboxes: create support@trydoppl.com and

    monitored.

0.7 [YOU][WAIT ~days] Billing provider (only if charging at launch): apply to

    sales tax/VAT for you) or Stripe. Approval needs the entity from 0.5.

PART 2 — DOMAIN & DNS
================================================================================
You need one DNS record for the backend, and (for the download site) a way to
publish static files.

2.1 [YOU] Log in to wherever trydoppl.com's DNS is managed (the registrar or
    Cloudflare, if you use it).

2.2 [YOU] After you have the server's IP (PART 3), add ONE record:
      Type: A
      Name: api          (this makes api.trydoppl.com)
      Value: <SERVER-IP>
      TTL: automatic / 300
    If your host gives you an IPv6 address too, also add an AAAA record with the
    same Name "api" and the IPv6 value.

2.3 [WAIT ~5–60 min] DNS propagates. Check with:
      [TERMINAL] dig +short api.trydoppl.com
    It should print your server IP. HTTPS certificates (PART 4) only work AFTER
    this resolves.

2.4 NO domain yet and just want to test? The deploy tool supports a no-domain
    mode that gives you real HTTPS at api.<ip-with-dashes>.sslip.io — fine for a
    private test, not for public links. See PART 4.5.

PART 3 — BACKEND HOSTING: ORDER THE SERVER
================================================================================
The cheapest honest production setup is ONE virtual machine. The app's hosted
plane is designed to run on a single box (the "sharded-SQLite tier"); it was
load-tested at 10,000 users on one machine.

3.1 [YOU] Create a Hetzner Cloud account (console.hetzner.cloud). (Alternatives:
    DigitalOcean, Linode/Akamai, AWS Lightsail — any Ubuntu VM works; Hetzner is
    the cheapest by a lot.)

3.2 [YOU] Create a project, then "Add Server":
      - Location: closest to most of your users.
      - Image: Ubuntu 24.04.
      - Type:
          * CX22 (2 vCPU, 4 GB RAM, 40 GB disk) — ~€3.79/mo — fine for a small
            beta (tens to low hundreds of users).
          * CX32 (4 vCPU, 8 GB, 80 GB) — ~€6.80/mo — recommended starting point
            for a real beta / early public.
      - SSH key: add your public key (see 3.3). Do NOT use password login.
      - Backups: tick the "Backups" box (+20%, ~€1.40/mo). One click, worth it —
        this is your safety net in addition to Cortex's own backups.
      - Create. Note the server's public IP.

3.3 [TERMINAL] If you don't have an SSH key yet, on your Mac:
      ssh-keygen -t ed25519 -C "you@trydoppl.com"
      (press Enter through the prompts; then paste ~/.ssh/id_ed25519.pub into
      Hetzner's SSH-key field). Confirm you can log in:
      ssh root@<SERVER-IP>            # type "yes" once; you should get a shell
      exit

3.4 Disk sizing rule of thumb: each user's data (their memory shard slice +
    vault files + backups) is small at first but grows. 80 GB comfortably holds
    hundreds to low thousands of active users. When "df -h" on the box passes
    ~70% full, resize the VM to a bigger disk (Hetzner does this in-place in
    minutes) or move to the bigger dedicated box in PART 16.

PART 4 — BACKEND HOSTING: DEPLOY CORTEX (ONE COMMAND)
================================================================================
Everything below runs FROM YOUR MAC, inside the repo. The repo already contains a
complete deploy kit under deploy/ that does all the server setup for you.

4.1 [TERMINAL] On your Mac, in the repo folder:
      cd <path-to>/cortex/taipei        # the folder containing deploy/ and backend/
      git pull                          # make sure you have the latest
      ls deploy/                        # you should see push.sh, bootstrap.sh, etc.

4.2 [TERMINAL] Run the deploy (replace the IP and domain):
      deploy/push.sh root@<SERVER-IP> api.trydoppl.com

    What this does, automatically, on the server (you don't type any of it):
      - Uploads the current committed code to /srv/cortex/releases/<timestamp>.
      - Hardens the OS: firewall (only SSH + HTTPS open), disables SSH password
        login, installs automatic security updates + fail2ban.
      - Installs Caddy, which gets a REAL HTTPS certificate for api.trydoppl.com
        automatically (this is why DNS in PART 2 must resolve first).
      - Creates a Python virtual environment and installs the backend's
        dependencies.
      - GENERATES YOUR SECRETS ONCE: the operator admin token, the per-user
        encryption KEK, and a signing key. THESE ARE PRINTED AT THE END — copy
        them somewhere safe immediately (PART 6).
      - Installs systemd services so the API and the background worker run 24/7,
        restart on crash, and start on reboot.
      - Sets up a nightly backup timer.
      - Runs a health check and tells you the result.

4.3 [YOU] When it finishes it prints a block like:
      Admin token : cxop_....................
      KEK (escrow offline + password manager): <base64>
      API         : https://api.trydoppl.com
    COPY THE ADMIN TOKEN AND THE KEK NOW. You will not be shown them again.
    See PART 6 for exactly what to do with them.

4.4 The beta profile is on by default in deploy/cortex.env.example:
      - Accounts enabled.
      - CORTEX_AUTH_AUTOVERIFY=1 (no email server needed for beta).
      - On-device embeddings (model2vec) — zero AI API cost, private.
      - Rate limits + per-user quotas set to sane non-zero values.
      - Per-user encryption on (KEK from /etc/cortex/kek).
    To change any of these later, edit /etc/cortex/cortex.env on the server and
    run: systemctl restart cortex-api cortex-worker

4.5 [TERMINAL] No domain yet (quick test only):
      deploy/push.sh root@<SERVER-IP> --sslip
    It prints the api.<ip>.sslip.io URL it set up, with real HTTPS. Re-run with a
    real domain later; it's non-destructive.

4.6 [TERMINAL] To deploy a NEW version of the code later (after git pull):
      deploy/push.sh root@<SERVER-IP> --update
    This snapshots the databases first, switches to the new code, smoke-tests it,
    and AUTO-ROLLS-BACK if the smoke test fails. Safe to run anytime.

PART 5 — VERIFY THE BACKEND IS HEALTHY
================================================================================
5.1 [TERMINAL] From your Mac:
      curl https://api.trydoppl.com/health
    Expect JSON with "status":"ok". If you get a certificate error, wait a minute

5.2 [TERMINAL] Readiness (checks the multi-tenant runtime is correctly set up):
      curl https://api.trydoppl.com/ready
    Should return a JSON contract with status "ok". If it says "blocked", read

    (e.g. rate limit is zero, KEK missing). Fix in /etc/cortex/cortex.env and
    restart.

5.3 [TERMINAL] Create your first real account through the API to prove it works
    end to end (in beta autoverify mode this immediately activates):
      curl -X POST https://api.trydoppl.com/v1/auth/signup \
        -H "Content-Type: application/json" \
        -d '{"email":"you@trydoppl.com","password":"<a-long-password>"}'
      curl -X POST https://api.trydoppl.com/v1/auth/login \
        -H "Content-Type: application/json" \
        -d '{"email":"you@trydoppl.com","password":"<a-long-password>"}'
    The login should return an access_token starting with "cxs_".

5.4 [YOU] Open https://api.trydoppl.com/account/signup in a browser — you should
    see the actual signup page. This is the front door your users use.

PART 6 — SECRETS, THE ENCRYPTION KEK, AND ESCROW (DO NOT SKIP)
================================================================================
Cortex encrypts each user's connector credentials with a key derived from a
master key called the KEK (Key Encryption Key). This is what makes "delete my
account" cryptographically final and protects a stolen backup.

6.1 THE GOLDEN RULE: If you lose the KEK, every user's encrypted data becomes
    permanently unreadable. If someone STEALS the KEK *and* a backup, they can
    read that data. So the KEK must be (a) never lost, (b) stored separately from
    the data backups.

6.2 [YOU] Right after deploy, take the KEK that was printed (also at
    /etc/cortex/kek on the server) and store TWO copies:
      - In your password manager (1Password/Bitwarden), labeled "Cortex KEK —
        production".
      - In a second offline place you control (an encrypted USB drive, a sealed
        printout in a safe). NOT in the same cloud as your server backups.

6.3 [YOU] The admin token (cxop_...) is the operator master key for the control
    plane (provisioning, admin endpoints). Store it in your password manager too.
    Never give it to a user, never put it in the app.

6.4 On the server, permissions are already set (KEK file is root:cortex, mode
    0440). Do NOT loosen them. The nightly backup job intentionally EXCLUDES the
    KEK so a stolen backup stays unreadable — keep it that way.

6.5 Before you ever tell users their data is "encrypted," make sure you have
    done a restore drill (PART 12.4) proving you can recover with your escrowed
    KEK. Claiming encryption you can't restore is worse than not claiming it.

PART 7 — ACCOUNTS: HOW THEY WORK + GOOGLE/GITHUB LOGIN
================================================================================
7.1 What already exists (no work needed): email+password signup and login,
    sessions with automatic refresh and revocation, self-serve API/MCP token
    minting, password reset, account deletion (with crypto-erasure of keys), and
    a browser front door at /account/*. Each account gets its own isolated,
    encrypted data store.

7.2 [BETA] With CORTEX_AUTH_AUTOVERIFY=1 (the default in the deploy kit), a new
    account is active immediately at signup — no email needed. Good for a closed
    beta. TURN THIS OFF for public launch (PART 8.5).

7.3 Turn on "Continue with GitHub" (5 minutes, no review):
    a. [YOU] github.com → Settings → Developer settings → OAuth Apps → New OAuth
       App.
       - Application name: Cortex
       - Homepage URL: https://trydoppl.com
       - Authorization callback URL:
           https://api.trydoppl.com/v1/auth/oauth/github/callback
       - Register, then "Generate a new client secret".
    b. [TERMINAL] On the server, edit /etc/cortex/cortex.env and set:
           CORTEX_OIDC_GITHUB_CLIENT_ID=<the client id>
           CORTEX_OIDC_GITHUB_CLIENT_SECRET=<the client secret>
    c. [TERMINAL] systemctl restart cortex-api
    d. The GitHub button now appears automatically on /account/login.

7.4 Turn on "Continue with Google" (needs the review from PART 0.3):
    a. [YOU] Google Cloud Console → APIs & Services → Credentials → Create OAuth
       client ID → Web application.
       - Authorized redirect URI:
           https://api.trydoppl.com/v1/auth/oauth/google/callback
    b. [YOU] Configure the OAuth consent screen; add your privacy policy + terms
       URLs (PART 14); submit for verification. Until it's verified you can still
       test with up to 100 users.
    c. [TERMINAL] Set in /etc/cortex/cortex.env:
           CORTEX_OIDC_GOOGLE_CLIENT_ID=<...>
           CORTEX_OIDC_GOOGLE_CLIENT_SECRET=<...>
       Then: systemctl restart cortex-api

7.5 Existing (pre-account) users, if any: there is an operator "invite/claim"
    flow so a user who was provisioned before accounts can attach a login to the
    SAME data. If you have no such users, ignore this. If you do, contact them
    with a claim link generated via the admin endpoint (see APPENDIX C).

7.6 Sessions & security defaults already in place: passwords hashed with
    argon2id; login is enumeration-resistant (won't reveal if an email exists);
    reused refresh tokens revoke the whole session family; a session token can
    NEVER call admin or MCP endpoints. You don't need to configure any of this.

PART 8 — EMAIL DELIVERY (REQUIRED FOR PUBLIC LAUNCH)
================================================================================
For a public launch you must turn OFF autoverify, which means verification and
password-reset emails must actually reach inboxes.

8.1 [YOU] Choose a provider: Postmark (easiest, great deliverability, ~$15/mo for
    10k emails) or Amazon SES (cheapest at scale, more setup). Create an account.

8.2 [YOU] Add a sending domain (e.g. trydoppl.com or mail.trydoppl.com) and add
    the DNS records they show you:
      - SPF (a TXT record)
      - DKIM (one or more CNAME records)
      - DMARC (a TXT record at _dmarc; start with p=quarantine)
    Verify them in the provider dashboard (turns green).

8.3 [YOU][WAIT days-weeks] Warm up: send yourself and a few friends real emails
    over a few days before you open public signups, so the domain isn't "cold."

8.4 [TERMINAL] On the server, set in /etc/cortex/cortex.env:
      CORTEX_AUTH_EMAIL_MODE=smtp
      CORTEX_SMTP_HOST=smtp.postmarkapp.com     # or your provider's host
      CORTEX_SMTP_PORT=587
      CORTEX_SMTP_USERNAME=<provider username / token>
      CORTEX_SMTP_PASSWORD=<provider password / token>
      CORTEX_SMTP_FROM_ADDR=Cortex <hello@trydoppl.com>
    Then: systemctl restart cortex-api
    (If you set mode=smtp but leave the host blank, the server safely falls back
    to logging — it won't break signup, but no email will send. So set the host.)

8.5 [TERMINAL] Turn OFF beta autoverify for public launch, in the same env file:
      CORTEX_AUTH_AUTOVERIFY=0
    Restart. Now new users must click the verification link in their email.

8.6 [YOU] Test the real thing: sign up with a Gmail AND an Outlook address you
    own, confirm the verification email lands in the INBOX (not spam), the link
    activates the account, and password reset works. Do this before opening
    signups.

PART 9 — THE macOS APP: NOTARIZE IT (you're enrolled in Apple Developer)
================================================================================
Notarization is what makes the app open with a normal double-click instead of a
scary "unidentified developer" block. The tooling is already built into the repo
(macos/package_release.sh --production). You just need your Apple credentials.

9.1 [YOU] In Apple Developer, create a "Developer ID Application" certificate:
      - developer.apple.com → Certificates, IDs & Profiles → Certificates → "+"
      - Type: "Developer ID Application". Follow the prompts (you'll create a
        certificate signing request from Keychain Access → Certificate Assistant).
      - Download and double-click the .cer to install it into your login keychain.
    [TERMINAL] Confirm it's there and note its exact name:
      security find-identity -v -p codesigning
    It shows a line like: "Developer ID Application: Your Name (TEAMID)". Copy
    that whole quoted string.

9.2 [YOU] Create an app-specific password for notarization:
      - appleid.apple.com → Sign-In & Security → App-Specific Passwords → generate
        one, label it "cortex-notary". Copy it.

9.3 [TERMINAL] Store notary credentials once (replace the three values):
      xcrun notarytool store-credentials cortex-notary \
        --apple-id "<your-apple-id-email>" \
        --team-id "<TEAMID>" \
        --password "<the app-specific password>"

9.4 [TERMINAL] Build the signed, notarized, stapled DMG:
      cd macos
      CORTEX_CODESIGN_IDENTITY="Developer ID Application: Your Name (TEAMID)" \
      CORTEX_NOTARY_PROFILE=cortex-notary \
      CORTEX_BUNDLE_PYTHON=1 \
      ./package_release.sh --production
    This signs the app with a hardened runtime, submits it to Apple, WAITS for
    the result, staples the ticket, and verifies with spctl. It produces the DMG
    + a checksums file + a latest.json update manifest under the outputs folder.

9.5 [IF THE FIRST SUBMISSION IS REJECTED] Apple sometimes rejects a bundled-
    Python app on the first try for a missing "hardened runtime" entitlement
    (e.g. allow-unsigned-executable-memory / disable-library-validation).
    notarytool's log will name the exact issue. This is a small entitlements
    addition to the signing step — if it happens, that's the fix; re-run 9.4.

9.6 [TERMINAL] Sanity check the result opens cleanly:
      spctl -a -t open --context context:primary-signature -v <path-to>.dmg
    (Should say "accepted".) On a clean Mac, the app should now open with a
    double-click.

9.7 For a BETA you can skip 9.1–9.6 and ship the unnotarized DMG; tell testers:
    "Right-click Cortex.app → Open → Open" the first time (macOS Sequoia/26:
    if double-click is blocked, go to System Settings → Privacy & Security →
    scroll down → 'Open Anyway')."

        Keeps large binaries out of git and downloads cheap.
     NOTE: today the repo has an OLD unnotarized DMG committed in site/downloads/.
     Replace it with your freshly notarized one from PART 9 before publishing.
     There's a checker you can run to validate the site is consistent:
       [TERMINAL] python3 scripts/check_distribution_site.py

     click Download, confirm the DMG downloads and its checksum matches the
     checksums file.

10.4 Auto-update (nice-to-have, not required for launch): the build produces a
     latest.json manifest. Wiring the app to a real auto-updater (Sparkle) is a
     follow-up; for launch, users just download the new DMG. Note this in your
     "how to update" FAQ.

PART 12 — BACKUPS, MONITORING, ALERTING
================================================================================
12.1 Cortex's own nightly backups are already installed by the deploy kit
     (systemd timer cortex-backup). They make consistent SQLite snapshots + copy
     the vaults, keep 7 nights locally, and EXCLUDE the KEK.

PART 21 — GLOSSARY
================================================================================
KEK — Key Encryption Key: the master key that protects each user's data key.
      Escrow it; never lose it; keep it off the backups.
Shard — one of 16 database files that user data is split across on the box, for
      isolation and performance. Automatic; you don't manage it.
Notarization — Apple's automated malware scan that lets the app open without a
      warning. One command once you have a Developer ID cert.
OIDC / OAuth — the standard behind "Sign in with Google/GitHub."
cxs_ / cxr_ — a user's session (access) and refresh tokens. Short-lived,
      auto-refreshed by the app. Not something you handle.
cxop_ — YOUR operator admin token. Master key for the control plane. Guard it.
Autoverify — beta setting that activates accounts at signup without email. OFF
      for public launch.
Sharded-SQLite tier — running everything on one box (the sanctioned setup for up
      to ~10k users). Upgrades to dedicated hardware, then Postgres, later.

APPENDIX B — COMMON FAILURES AND FIXES
================================================================================
"curl https://api... certificate error" → Caddy is still issuing the cert, or DNS
   isn't resolving yet. Wait a minute; confirm `dig +short api.trydoppl.com`
   returns your IP; check `journalctl -u caddy`.
"/ready says blocked" → read the "checks" array; each blocked check's "detail"
   says exactly which env var to set. Common: rate limit/quota is 0, or KEK not
   configured.
"Signup works but no email arrives" → mode isn't smtp, or SMTP host/creds wrong,
   or DNS (SPF/DKIM) not verified, or the domain is cold (spam). Check
   `journalctl -u cortex-api` for send warnings; test the provider separately.
"App won't open on a tester's Mac" → not notarized: right-click → Open, or System
   Settings → Privacy & Security → Open Anyway. Fix permanently by notarizing.
"App can't reach hosted backend" → the URL must be https and reachable; check the
   endpoint field is exactly https://api.trydoppl.com and /health works in a
   browser.
"Worker not processing" → `systemctl status cortex-worker`; restart it; check
   disk isn't full (`df -h`).
"Disk filling up" → prune old backups, or resize the VM; set the disk alert.
